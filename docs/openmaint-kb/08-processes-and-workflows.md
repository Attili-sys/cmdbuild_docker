# 08 — Processes and Workflows

**Source:** API `/processes`, `process-details.json`, lookup `Process - ProcessStatus`  
**Classification:** STANDARD OPENMAINT

---

## Process Class Hierarchy

```
Activity  [abstract — root for all workflow processes]
  └── Process  [abstract]
        └── MaintProcess  [abstract — maintenance processes only]
              ├── CorrectiveMaint  [ACTIVE — corrective maintenance workflow]
              └── PreventiveMaint  [ACTIVE — preventive maintenance workflow]
```

Only `CorrectiveMaint` and `PreventiveMaint` are startable (non-abstract) process classes.

## CorrectiveMaint — Process States

From the `Process - ProcessStatus` lookup (16 values, CM-prefixed):

```
CM-Opening
    ↓ [requester submits request]
CM-Assignment
    ↓ [maintenance office assigns team]
CM-Management
    ↓ [technician reports execution start]
CM-Estimate
    ↓ [technician or supplier provides cost estimate]
CM-Control
    ↓ [supervisor reviews and approves]
CM-Closure  [process ends — Positive / Negative / Canceled]
```

### Process Actions (from `Process - Action` lookup, 31 values)

Key CM actions visible at each state:

| State | Actions |
|-------|---------|
| CM-Assignment | Advance, Split (create subtask), Duplicate, Reject |
| CM-Management | Advance, suspend (SuspensionReason) |
| CM-Estimate | Advance, handle empty costs warning |
| CM-Control | Advance, handle empty subtasks warning |

Additional action values indicate notification triggers and delay management (`CTX-DelayNotificationManage`).

### Corrective Maintenance Process Attributes

The CM process carries:
- Opening date, execution dates, closure date
- Priority (1–4)
- Type: Breakdown / Damage / Extraordinary
- Linked CI (asset), site, room
- Assigned team, company, employees
- Requester reference
- Estimate status: CM-Accepted / CM-Rejected / CM-Received / CM-Expected / CM-Declined
- Outcome: Positive / Negative / Canceled
- Suspension reason: Supplier / Replacement / Other
- SLA state (Ongoing / Paused / Concluded)
- Accounting movements (labour, material, generic costs)
- Warehouse movements (material usage)
- Attachments

## PreventiveMaint — Process States

PM processes are auto-generated by the scheduler. PM states include:
- `PM-Execution` — the active execution state
- PM processes are opened with planned dates and assigned team

PM processes carry:
- Reference to PrevMaintConfig (schedule)
- Expected and actual execution dates
- Tasks (checklist items) from PrevMaintDef
- Task outcomes: Ok / Ko / Done / ToDo
- Accounting costs
- Warehouse material usage
- Technician signature/notes

## XPDL Workflow Definitions

openMAINT process workflows are stored as XPDL (XML Process Definition Language) in the database. The workflow engine executes these definitions.

The XPDL definitions are not stored as files — they are embedded in the database. They can be exported via the CMDBuild admin UI (Administration → Processes → edit → export) or via API.

The XPDL defines:
- Activities (steps)
- Transitions (allowed state changes)
- Role assignments
- Scripts (Groovy/JavaScript embedded in transitions)
- Email notification triggers
- Form field visibility per state

**NOT CONFIRMED:** The exact XPDL content for CorrectiveMaint and PreventiveMaint was not extracted in this inspection. The state machine above is derived from the `Process - ProcessStatus` and `Process - Action` lookup values.

## Automatic Scheduling (PM Only)

Two scheduled jobs manage PM work orders automatically:

| Job | Cron | Purpose |
|-----|------|---------|
| `PrevMaintGeneratorScheduler` | `00 05 * * ?` (05:00 UTC daily) | Generates PM work orders when `FirstOpeningDate` is reached |
| `PrevMaintAdvanceScheduler` | `00 06 * * ?` (06:00 UTC daily) | Advances PM processes to execution state automatically |

These jobs are enabled in the demo configuration.

## Email Notifications

The `MaintProcReplyEmailMgt` job (disabled in demo — no email accounts configured) handles:
- Receiving reply emails and mapping them to process actions
- Configured via `_Job` table with complex JSON config for INBOX folders, key/value XML parsing, etc.

Email templates (`_EmailTemplate`) exist for maintenance process state changes. `NOT CONFIRMED` — exact templates were not enumerated in this inspection.

## Multi-role Process Participation

Process steps are assigned to roles:

| Role | Typical activity |
|------|-----------------|
| `Requester` | Opens CM request (CM-Opening) |
| `MaintOffice` | Assigns team (CM-Assignment) |
| `Team` | Executes maintenance (CM-Management) |
| `Supplier` | May participate in estimate (CM-Estimate) |
| `AdminOffice` | Reviews and controls (CM-Control) |
| `SuperUser` | Full access to all states |

## Survey / Feedback

After closure, a `Survey` can be sent to the requester to rate:
- Satisfaction (1–5)
- Quality (1–5)
- Agreement (1–5)

Survey is linked to the process via `Map_ProcessSurvey`.

---

## Process Flow Logging

`ProcessFlowLog` (SimpleClass) records process execution steps. This is the CMDBuild audit trail for workflow transitions.

## Extending the Process Model for AJMN

To add new maintenance-related workflows:

1. **New process type** (e.g., `ServiceRequest`): Create a new process class inheriting from `MaintProcess` or `Process`. Design XPDL workflow. Assign roles.
2. **Existing process customization**: Modify role assignments, add attributes, adjust states in XPDL.
3. **HSE workflows**: Not currently present. Would require new process classes — see `18-ajmn-fit-gap.md`.
4. **Approval chains**: CM already has a Control/approval state. Custom multi-level approval would require XPDL modification.

Classification of these changes: **LOW-CODE** (XPDL design via admin UI) for new processes, **CUSTOM DEVELOPMENT** for complex multi-step approval chains.
